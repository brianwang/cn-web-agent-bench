# cn-web-agent-bench v0.1 评测报告

> 运行时间：2026-11-20
> 配置：10 个任务 × 3 轮 = 30 次运行
> Agent：LLM（deepseek-v4.1-flash）+ Playwright，复用已登录 Chrome（CDP）
> 环境：Linux，Chrome，低频访问

| 指标 | 数值 |

| 成功 | 11 次（**37%**） |
| 平均耗时 | 37.6s |

## 关键发现

### 1. 登录墙是第一阻碍

6 个任务（T04/T05/T07/T10 及 T03 部分）失败于登录相关。其中：

- **PDD 商家后台**：0/3，全是 login。登录态有效期实测 < 6 小时。
- **抖音创作者中心**：0/3，全是 login。即使复用已登录 Chrome，仍被要求重新验证。
- **1688**：**3 轮全部 login，但此前单轮测试 2 次都成功**——说明平台风控有状态波动。
- **闲鱼**：1/3，未登录搜索弹「请先登录」。

### 2. 平台状态会随时间波动

同一任务在不同时间运行，结果可能完全不同：

- 1688：早先 2/2 成功 → 3 轮 0/3
- 小红书：早先 1/1 成功 → 3 轮 0/3（全部验证码）
- 12306：早先曾误判失败 → 修检测后 3/3

**结论：单次运行结果不可作为 benchmark 数据，必须多轮 + 记录时间。**

### 3. 验证码是随机出现的

小红书从「能读公开笔记」到「3 次全验证码」，说明平台对自动化访问有随机挑战机制。

### 4. 渲染失败集中在重前端页面

淘宝 82s 平均耗时、2 次 js-render 失败——SPA 页面加载慢，固定等待策略不够。

### 5. 有登录态的任务反而快

知乎（T02）15.4s、1688（T05）12.7s——**登录态存在时，任务在 15 秒内完成**。慢的都是要等渲染或对抗风控的。

## 方法论

1. **只读任务**：查、看、搜，不发布、不下单
2. **结构化阻塞**：`login / slider / captcha / anti-bot / js-render / timeout`
3. **多轮取平均**：单轮不可信
4. **复用真实浏览器**：CDP 连接已登录 Chrome，不用全新 profile

## 局限

- 样本量小（每任务 3 轮），置信度有限
- 只测了 10 个平台，代表性有限
- Agent 用的是通用 LLM + 简单循环，不代表最优 agent 设计
- 平台随时改版，数据有保质期
